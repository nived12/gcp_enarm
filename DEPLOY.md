# Deploying GPCEnarm

Railway, one service, Postgres attached. Solid Queue runs inside Puma
(`bin/boot` sets `SOLID_QUEUE_IN_PUMA`), so there is no Redis and no second process
to supervise.

This file exists because the interesting part of deploying this app is not the
deploy — it is **moving a corpus that takes two hours to scrape, and never
regenerating questions that cost real money.** Both are easy to get wrong once, and
expensive to get wrong twice.

## What lives where

| Data | Where it comes from | Cost to reproduce |
|---|---|---|
| Specialties / branches / topics | `db/seeds/taxonomy.yml`, seeded on every deploy | free, automatic |
| Guidelines + section text | scraped, or imported from a file | **~2 hours, ~3,800 requests** |
| Recommendations | parsed from section text | seconds |
| Guideline↔topic links | matched from titles | seconds |
| Clinical cases + questions (Phase 2) | generated by an LLM | **$5–55, and not reproducible** |

The rule that follows from the last two rows:

> **Scraped text moves between environments. Everything derived from it is rebuilt.
> Generated questions are produced once and backed up — never regenerated.**

Rebuilding derived data on arrival is not only smaller, it is more correct: production's
recommendations are parsed by production's parser, rather than frozen at whatever the
parser said on the day the file was written.

## First deploy

1. Railway project → add **PostgreSQL** → deploy this repo. `railway.json` builds the
   `Dockerfile` and starts `./bin/boot`, which runs `db:prepare`, `db:seed` and the server.
2. Set `RAILS_MASTER_KEY` from `config/master.key`. Without it the app cannot read
   credentials and will not boot.
3. Set anything from `.env.example` the phase you are on needs. Nothing there is required
   to boot.
4. Confirm the taxonomy seeded: `railway run bin/rails runner 'puts Topic.count'` → 230.

At this point the app runs and has its taxonomy, and no guidelines.

## Moving the GPC corpus into production

Do this instead of scraping again. A second full crawl costs two hours and puts ~3,800
requests on a small government server and a rate-limited archive for no new information.

```bash
# 1. On the machine that has the corpus (currently your laptop).
bin/rails "gpc:export[tmp/gpc-corpus.jsonl.gz]"

# 2. Load it into Railway's database. railway run injects the service's environment
#    variables and runs locally, so the file stays on your machine — no upload.
railway run bin/rails "gpc:import[tmp/gpc-corpus.jsonl.gz]"

# 3. Rebuild what the file deliberately does not carry.
railway run bin/rails gpc:reparse gpc:link
```

Without the Railway CLI, step 2 is the same task against an explicit URL — and it must
be Railway's **public** Postgres URL, since you are connecting from outside their network:

```bash
DATABASE_URL="postgresql://…proxy.rlwy.net:PORT/railway" bin/rails "gpc:import[tmp/gpc-corpus.jsonl.gz]"
```

`gpc:import` is idempotent and keys on `catalog_key`, so running it over a database that
already has the corpus updates rather than duplicates. Sections reference their guideline
by catalog key, never by row id — the two databases number their rows independently.

## Scraping from scratch, if you ever must

```bash
railway run bin/rails gpc:catalog   # the 53 live guidelines
railway run bin/rails gpc:ingest    # their sections — ~3,100 requests, ~1 hour
railway run bin/rails gpc:archive   # ~694 archived PDFs — slower, and the archive throttles
railway run bin/rails gpc:link
```

`gpc:ingest` and `gpc:archive` enqueue Solid Queue jobs on the `ingestion` queue, which is
pinned to one thread in `config/queue.yml`. Leave it that way. The Internet Archive answers
429 and 503 freely and will need more than one attempt.

## Keeping it fresh

The live catalog changes — `SS-757-25` appeared after the first survey. Re-running
`gpc:catalog` then `gpc:ingest` is safe at any time: a guideline whose `content_hash` is
unchanged has only its `ingested_at` touched, so "we checked today" and "they republished"
stay distinct facts, and only the second should ever invalidate generated questions.

## Tasks you will want and may not remember exist

| Task | What it is for |
|---|---|
| `gpc:reparse` | Re-read stored section text through the current parser. Use after any parser change — it does not touch the network. |
| `gpc:retitle` | Re-derive archived titles from stored text. Same idea, for the PDF title heuristic. |
| `gpc:export` / `gpc:import` | Move the corpus between environments. |
| `taxonomy:seed` | Rebuild the topic tree after editing `db/seeds/taxonomy.yml`. Runs automatically on deploy. |

## Before the first paying subscriber

- Turn on Railway's Postgres backups. After Phase 2 the database holds questions that
  cost money and cannot be regenerated identically.
- Re-read the licensing note in the plan. GPC content is licensed for non-commercial
  teaching use; the mitigation is architectural — we generate original cases that cite a
  guideline, and never redistribute guideline text as the product. Worth a lawyer's
  fifteen minutes.
